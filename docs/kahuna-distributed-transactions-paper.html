I. A Transaction Crosses Many Boundaries

A key–value transaction has a small interface and a long path. One logical operation can touch several key ranges. It can be forwarded to different Raft leaders. It can enter several actor mailboxes. It can outlive the request that started it, race a range split, or be retried after the client lost the reply. The transaction layer must make all of these mechanisms agree on one outcome, and it must keep the common case cheap.

Kahuna's answer is a layered protocol, and Figure 1 is its map. An in-memory coordinator owns the live transaction and its operation history. Key actors stage tentative values and point locks. At commit, persistent effects become replicated prepared intents. A canonical record on an anchor partition chooses commit or abort exactly once. Materialization into ordinary storage may happen after the client has its answer, because every read understands an unresolved intent. Background recovery, range-reconfiguration barriers, and idempotent replay finish the protocol after failures.

This note is written to be walked, not skimmed. Follow the token around the loop. Each station lights the sentence that explains it, Table I counts what each shape of commit costs in consensus barriers, and Table II names the anomaly that each decision defends against. Statements about fewer barriers or fewer allocations follow from the code path; they are not substitutes for measurements. The analyzed release set is Kahuna 1.5.3, Kommander 1.4.4, Nixie 1.3.0, and CamusDB 0.11.1. Source code and repository documentation are the artifact of record [1, 2, 4, 12].

II. Two Kinds of Keys, Two Interfaces

Storage, processes, and failures

Kahuna partitions the key space. A routing layer maps a key or a range to a logical partition, and then to the current Raft leader for that partition. Kommander supplies replicated logs, leadership, quorum durability, replay, and snapshot installation [2, 3]. Nixie supplies bounded-mailbox actors [4]. A per-key actor serializes local state transitions. An off-mailbox partition scheduler submits replicated writes, so a slow quorum does not block unrelated actor messages.

The protocol assumes crash failures, message loss or delay, retries, leader changes, and range splits or merges. It does not make progress without a quorum for the required partition. Hybrid logical clocks (HLC) give a compact, causality-respecting time domain [5]. They do not give Spanner-like bounded clock uncertainty or external consistency [6]. Local monotonic clocks measure elapsed time and admission aging. Distributed ordering and durable deadlines are HLC values.

There are two durability classes:

  • Persistent keys are represented in Raft and later flushed to the configured backend (memory, SQLite, or RocksDB). Raft, not the backend flush, is the immediate durability authority.
  • Ephemeral keys live in memory. Their staging and two-phase coordination never become crash durable.

A transaction configured for durable decisions rejects any modified ephemeral key. A best-effort transaction may mix the classes, but only its persistent subset is recoverable: a crash between persistent finalization and ephemeral application can expose a partial cross-class outcome. The API makes this boundary visible instead of implying an atomicity that the storage substrate cannot give.

Script and interactive transactions

Script transactions execute a parsed, server-side sequence. A single statement takes the direct non-transactional path. A multi-statement or explicit BEGIN … COMMIT END block uses the coordinator. Listing 1 shows the shape that the rest of this note follows.

BEGIN (locking=optimistic, decisionDurability=durable)
  LET src = GET acct/a
  LET dst = GET acct/b
  IF to_int(src) >= 10 THEN
    SET acct/a to_int(src) - 10
    SET acct/b to_int(dst) + 10
  END
  COMMIT
END

Listing 1. A durable optimistic transfer. Optimistic locking implies read-set validation, so the two GETs form the read set, and each SET carries the base revision it was computed from. If acct/a and acct/b sit on one partition, the whole commit is one Raft proposal.

Interactive transactions expose begin, read, write, scan, commit, and rollback calls over gRPC or the embedded API. The server, not the client, owns the authoritative working set. A handle carries the transaction identifier, the coordinator key, and, after the first confirmed persistent mutation, the durable record's anchor key. REST exposes script execution and single key operations, but not the interactive session lifecycle.

The distinction matters after an ambiguous network outcome. A client-provided list of writes is never accepted as a substitute for the server's staged state. Reusing the same handle and operation identity lets the server answer from the live session, from a bounded terminal-result cache, or from the canonical durable record.

III. Who Owns What

The normal path has four ownership layers:

client request
  → session coordinator + operation registry
  → range router → current Raft leader
  → per-key actor: MVCC state, lock, staged value
  → partition batch scheduler → Kommander Raft

The coordinator owns transaction-wide facts: timeout, priority lease, read policy, locking policy, participant set, range locks, read observations, operation results, and finalization state. Key actors own key-local facts: committed revisions, the transaction's staged revision, point locks, write intents, and prepared-intent overlays. This split keeps a process-wide transaction object out of the hot key path while it keeps one authority for commit.

Routing carries a range generation. A write is fenced when it first reaches its key owner, and again immediately before a queued replication batch is flushed. The second check is essential. A proposal can wait in a batch long enough for a split, a merge, or a leader move to invalidate its original route.

Several replicated control structures support the data plane: a range map and generation fence decide ownership; snapshot holds publish an MVCC retention floor; transaction records store canonical decisions; prepared-intent records store participant effects; completion evidence and transaction metadata survive cache eviction, replay, and range transfer; and application-durability floors stop Raft log compaction from outrunning asynchronous backend persistence. These structures turn local optimizations, such as caches and asynchronous materialization, into recoverable state machines.

Admission and overload

Before a script or a session begins, it enters a per-node priority gate. The script gate and the session gate are separate, so one workload shape cannot consume the other's whole allowance. Configurable maximum concurrency, queue depth, and admission wait bound resource use. Reserved slots protect high and critical priorities. Monotonic aging improves queue progress, although the original priority still controls access to reserved capacity.

Admission is a load-shedding mechanism, not a correctness mechanism. It neither preempts an active transaction nor changes lock conflict rules. An AdmissionRefused answer means that no transaction began, and the caller may back off. Session lifetime is clamped independently. The defaults are a 5 s transaction timeout, a 300 s maximum, a 5 s admission wait, and a 30 s maximum wait. Priority admission can be disabled.

The replicated write scheduler has a second overload boundary. It bounds queued items and bytes per partition and globally. Terminal work, which means decisions, materialization, and settlement, has reserved capacity, so a flood of new writes cannot indefinitely stop already-decided transactions from releasing their intents.

IV. Begin and Operation Idempotency

Starting a transaction validates the option combination, acquires admission, creates an HLC-derived transaction identifier, and installs a session context. A fixed nonzero read timestamp cannot be combined with tracked latest-read validation, because the two mean different things: a historical as-of view versus a current-version dependency set.

Every interactive operation carries a 128-bit operation identifier and a digest of its request. Admission of an operation checks the operation table together with the finalization fence in one atomic step. The result is one of three cases:

  • new: the operation may execute;
  • pending: another copy is executing, so the caller joins its result;
  • completed: the saved response is returned and the effect is not applied again.

Reusing an identifier with a different digest is rejected. A participant-side cache handles the other half of the problem: a key actor applied an effect, but the coordinator did not record completion before the reply was lost. Request admission and effect application are therefore both idempotent, each at its own ownership layer.

Commit, rollback, and timeout reaping contend for one finalization slot. The winner closes the session to new operations, waits for earlier admitted operations to drain, freezes the transaction snapshot, and performs finalization. Concurrent finalizers observe the same result. This ordering stops a late write from entering after the participant manifest has been frozen.

V. Staging, Locks, and Reads

A transactional persistent write does not append an ordinary key–value entry to Raft. The key actor checks the conditions, acquires an exclusive point lock, and stores an MVCC entry that belongs to the transaction, together with a leased in-memory write intent. Later reads by the same transaction select that staged version. This gives read-your-writes without making uncommitted data visible to anyone else.

Client writes take the exclusive point lock in both locking modes. The modes differ in how reads are protected:

  • Pessimistic reads acquire exclusive point locks. Prefix scans acquire an exclusive prefix lock; range scans acquire a range lock, exclusive by default.
  • Optimistic reads take no read locks and record observations for validation. Optimistic locking implies read-set validation even when the explicit validation option is None.

The public point lock is exclusive, not shared. Shared per-key read locks are a planned extension, not an implemented guarantee.

MVCC reads and snapshot holds

Without a fixed timestamp, a read selects the latest visible committed revision plus the transaction's own staged value. With a fixed read timestamp tr, point reads and scans select the newest version at or before tr. This yields one historical as-of view across partitions, provided that the required history is retained.

A client that needs a long-lived historical view acquires a replicated, leased snapshot hold. If the live holds have timestamps h1, …, hn, the effective retention floor is

F = mini hi.

Pruning keeps the newest revision at or below F and every newer revision. Actors keep a bounded recent history in memory, 16 revisions by default plus the floor boundary. Deeper reads fall back to the materialized backend asynchronously instead of blocking an actor mailbox. Holds are leased and reaped after expiration.

This mechanism protects history availability, not the serialization of a historical read with a later write. A transaction that reads an old snapshot and then writes is not given optimistic current-version validation. Treat fixed-timestamp transactions as read-only unless the application supplies its own invariant.

VI. Four Questions Conflict Detection Separates

Kahuna deliberately separates four questions that are often conflated: who may stage a value, whether an observed version is still current, whether a predicate is protected, and whether a prepared write is based on the expected predecessor. Each question has its own station on the loop.

Point locks and dirty writes

An exclusive point lock and a write intent allow only one live transaction to stage a write for a key. This prevents dirty writes: conflicting writers wait or retry instead of silently overwriting each other's tentative state. The lock is leased and released on commit, abort, or reaping. Locks are actor-local and therefore fast, but their liveness depends on renewal and on leadership.

Locking alone is insufficient. A transaction can read before it takes a write lock, another transaction can commit, and the first can acquire the lock afterwards. Kahuna therefore remembers the base state of every read-before-write key and validates it again during durable preparation.

Read-set validation

Tracked reads record (key, exists, revision). If one transaction observes the same key with inconsistent base revisions, validation fails immediately. Keys that are also in the write set are excluded from ordinary read-set validation, because their stronger staged-base fence runs at prepare time.

At commit, the coordinator batches current-state probes across nodes and compares each observed key's existence and revision. A changed or deleted key aborts the transaction. Read-only transactions go through this path as well; skipping validation for an empty write set would admit classic read skew.

Validation runs after every durable prepare and before the commit decision. A failed validation therefore leaves durable intents that are safely abortable and recoverable, and it never exposes a tentative write.

The concurrent-writer and range-lock probe

Before read validation, the coordinator makes one batched conflict probe. It asks for undecided foreign writers on read-only keys, and for foreign range or prefix locks that cover keys this transaction writes. A missing probe response fails closed. Probing active writers first avoids two transactions that each wait for the other's read validation. The post-prepare range-lock check catches a write-fence lock, such as a split's or a merge's quiesce, that landed after the writer staged its value, because that lock mode steps around write intents by design.

A Shared or an Exclusive range lock does not step around them. Its acquire is refused, with the holder's transaction identifier, while any covered key carries an undecided write intent of another transaction. A write intent whose transaction is already decided but not yet settled is not a live writer: its outcome is durable, and every read resolves such an intent inline to the committed value, or on abort to the pre-image. A Shared acquire is therefore granted over it. An Exclusive acquire cannot place its own intent while the predecessor still occupies the slot, so it waits, but the actor names the blocked keys and settles those decided intents itself, so the wait is bounded by their resolution rather than by the settlement backlog. This is the reader-side half of strict two-phase locking. The write-path refusal, a mutation under a foreign range lock, is the other half. A lock and a write that overlap on a key can never both succeed, whichever arrives first.

Range locks are leader-local, in-memory leases. The coordinator renews them and reacquires them after a participant leader change. If the coordinator itself is lost, its session and its lock list disappear and the leases expire. The durable validation and decision machinery is the backstop. Range locks are not a globally replicated predicate-lock manager.

Staged-base fencing

For every non-blind persistent write, the prepared intent records whether the base existed and its revision. Kahuna checks this dependency in three layers:

  1. Pre-proposal check. The leader probes the current key state before it proposes the prepare. A foreign undecided intent yields a retry, not a guess.
  2. Apply-time fence. Every replica's prepared-intent state machine compares the validated base with its remembered last transactionally committed head. A competing commit in the probe-to-proposal window makes the prepare stale. The intent is installed deterministically, but the leader withholds a successful prepare acknowledgement, and the coordinator aborts.
  3. Replica stale-base veto. If a replica detects a stale base while it applies a prepare, it can drive a best-effort abort at the canonical anchor. This stops a stale leader from acknowledging a prepare that a fresher replica can prove invalid.

Blind writes carry an explicit sentinel instead of a base revision and keep last-writer-wins semantics. The third layer is recent hardening motivated by kill and failover campaigns. Unit and focused regression suites cover it, but the final multi-node fault soak has not established closure. Section XIII treats it as a promising defense, not as settled evidence.

Successful pessimistic transactions over correctly locked predicates protect both points and phantoms. VII. The Durable-Intent Commit

Frozen commit input

When persistent finalization starts, the coordinator builds an immutable commit input. It contains the transaction identifier and epoch; the coordinator key, anchor key, partition, and route generation; one canonical HLC commit timestamp; an absolute decision deadline; a hash and an explicit list of participant keys; and, per partition, the prepared intents with the exact final value or tombstone, the target revision, the expiration, and the validated base state.

The participant manifest stops recovery from committing a transaction for which only an accidental subset was prepared. Identity is the tuple (transaction, epoch, manifest hash). An exact replay is idempotent; a divergent replay under the same identity is rejected. The anchor is the partition of the first confirmed persistent mutation. Anchoring by key lets normal routing and range migration find the record without a separate global transaction service.

Two replicated state machines

The standard two-phase path

For a persistent transaction over arbitrary partitions, finalization proceeds as follows.

  1. Revalidate staged bases. Detect obvious lost updates before any consensus work is spent.
  2. Freeze serialization. Serialize each exact prepare delta once, so a retry cannot change bytes or meaning.
  3. Initialize and prepare. On the anchor partition, record initialization and the anchor key's prepare share one atomic Raft proposal. Every other participant partition prepares concurrently. Completion distinguishes “batch committed” from “this prepare acknowledged”, because the apply-time fence can commit the proposal while it refuses the prepare's logical success.
  4. Help blocked predecessors. If a key is occupied by a decided but unsettled intent, consult its canonical record, help materialize or clear it, and retry the idempotent prepare within a bound.
  5. Validate. After every prepare is quorum durable, run the foreign-writer and range-lock probe, then read-set validation.
  6. Decide. Propose commit or abort at the anchor. A routed canonical read decides the real compare-and-set winner; the sender's local projection is not treated as truth across a leader change.
  7. Resolve. Materialize committed effects or clear aborted ones, release locks, and settle the intent records. With deferred settlement, which is the default, this step continues after the durable decision has been returned.

Invariant. A visible durable commit implies that the canonical record is committed and that every persistent participant effect already exists as a quorum-durable prepared intent. It does not imply that every effect has been rewritten as an ordinary key–value entry in the backend.

The adaptive presumed-abort deadline

An undecided transaction must not block a key forever when its coordinator disappears. Kahuna observes recent finalization latency with a local monotonic timer and derives a window

W = clamp(m · p99, Wmin, Wmax),

where the default multiplier m is 4 and the default bounds are 5 s and 60 s. The absolute deadline is commit HLC + W. A fresh HLC attempt timestamp is checked at commit; an attempt beyond the frozen deadline cannot commit.

After the deadline, a participant leader may drive an abort tombstone at the anchor. The tombstone makes presumed abort durable and stops a delayed coordinator from later choosing commit. The observation window adapts to deployment latency, while the safety comparison lives in the replicated HLC domain instead of depending on synchronized wall clocks. The window is a liveness and safety trade-off: a short window aborts more during transient slowness; a long window keeps orphaned intents longer. Neither choice removes the need for an anchor quorum.

The single-partition fast path

If all persistent participants and the anchor sit on one partition, Kahuna can place record initialization, all prepares, and the commit decision in one atomic Raft proposal. Preflight checks foreign intents and validates reads; a late staged-base check narrows the last race before submission. When the coordinator leads the anchor partition it proposes the bundle locally. Otherwise it forwards the whole bundle to the anchor leader as one typed operation, which submits it atomically and answers with the canonical outcome read after the ordered apply: one extra network hop, still one durable round. After commitment, the leader installs the committed intent view before it replies.

The fast path is disqualified in a multi-process Raft group when the transaction has a read dependency beyond its written keys, or when a write carries a validated base whose safety would rely on a check performed before a possibly stalled proposal. This conservative rule stops a queued atomic bundle from applying after a conflicting update that occurred following validation. A single-process Raft group can relax some of these constraints, because there is no remote replica divergence and no inter-node proposal delay. The fast path is therefore not merely “one partition means one phase”. Eligibility includes the dependency footprint and the execution model, and when safety cannot be proven, the coordinator falls back to the standard protocol.

VIII. Reads Before Settlement

Synchronous materialization would extend client latency by one more replicated write for every participant. Kahuna instead separates the logical decision from the physical representation of committed data. Suppose that key k has the old committed value v0 and a prepared intent that contains v1 at commit timestamp tc.

Scans perform the same overlay across intents. A later writer must first resolve a committed predecessor before it derives a new revision or evaluates a condition; it cannot build on stale materialized state.

Settlement order

For commit, a resolver writes the intent's value as an ordinary transactional key–value log entry, waits for leader application, and only then atomically marks and removes the prepared intent. If any step fails, the intent remains and recovery retries. For abort, the resolver clears staged state and settles the intent without materializing a value. Every operation is identity checked and idempotent.

This ordering handles a crash after the decision but before materialization, after materialization but before the acknowledgement, and after the acknowledgement but before intent removal. In each case the durable record chooses the outcome, and at least one durable representation remains. Completion evidence lets a participant recognize an already committed operation after its actor state or its recent-result cache is gone. The evidence is carried through persistence and range transfer, so a key cannot lose its transaction identity by moving.

Recovery

Recovery sweeps prepared intents on the current leader of each participant partition:

  • Committed record: materialize and settle.
  • Aborted record: clear and settle.
  • Undecided before the deadline: leave it pending.
  • Undecided after the deadline: attempt a canonical abort.
  • Missing record after the permitted window: create an abort tombstone.

Every action rechecks the canonical compare-and-set result. A recovery worker that asks for abort but races a valid commit must follow the committed decision. The original coordinator is unnecessary once preparation and the anchor record are durable.

IX. Leader Change, Range Moves, and Storage

Leader changes

Actor caches and live locks are per node. They are not coherent across replicas. Correctness after promotion comes from replaying the deterministic transaction-record and prepared-intent state, and then from consulting those structures rather than a cache. Requests are routed to current leaders, and canonical record reads are re-routed when leadership changes.

The difficult case is a promoted replica with an orphaned prepared intent and an older per-key committed-head memory than another replica observed. The apply-time base fence only helps if the leader that evaluates the logical acknowledgement has the necessary history. The replica stale-base veto extends detection to every applying replica and asks it to force an anchor abort. This defense targets the gap directly, but its final partition and kill soak remains an open validation item.

Live range and point locks are not reconstructed as durable lock ownership. They expire or are reacquired by a surviving coordinator. Safety after a coordinator loss rests on durable prepared intents, base validation, the canonical decision, and recovery.

Range splits and merges

An intent cannot be moved like an ordinary value unless the destination also keeps everything needed to resolve it. Kahuna therefore uses a settle-before-cutover barrier:

  1. scan the moving interval for prepared intents;
  2. resolve every decided intent;
  3. refuse the transfer while an undecided intent remains or the scan cannot be trusted;
  4. transfer values, completion evidence, and remaining metadata;
  5. change the routing generation.

Materialization re-resolves the key's current partition instead of assuming the partition captured at prepare time. The two measures address opposite races: the barrier stops a move from dropping an overlay, and re-resolution stops a late resolver from writing to the old owner. Every queued write also carries its range generation and is rechecked at batch flush. A stale operation is released for a routing retry without contaminating the valid siblings in the same batch.

Raft versus materialized storage

Kommander's replicated WAL establishes the immediate durable order. A background writer later persists committed key revisions and transaction metadata to the selected backend. Reads can use resident replicated state before that flush. An application-durability floor stops Raft compaction from discarding log entries that the backend has not yet made independently recoverable. This separates consensus latency from backend write amplification, but it creates an invariant: snapshot and compaction policy must advance only behind materialization. Treating the backend as current merely because the client saw commit would be incorrect.

X. Why the Common Case Is Cheap

Heterogeneous partition batching

The partition scheduler accepts typed submissions, which are ordinary key writes, transaction records, and prepared intents, and coalesces independent operations headed to the same partition into one Kommander ReplicateEntries call. A default 1 ms oldest-item linger opens a small batching window. Batches are capped at 512 items and 4 MiB; an oversized valid item runs alone. One batch is in flight per partition, and different partitions progress concurrently.

Unlike transaction-level batching, this coalescing does not ask unrelated clients to share a transaction. Each item keeps its own result and range fence, while the shared proposal amortizes serialization, network, quorum, and WAL costs. A client cancellation stops the wait for that item but does not cancel a consensus batch shared with other clients. Accepted items complete exactly once at the scheduler boundary. Kommander can additionally group WAL work across partitions: Kahuna groups logical entries per Raft partition; the WAL layer may group physical persistence across partitions.

Barrier reduction and actor discipline

On the standard path, anchor initialization and the anchor prepare share a proposal, and non-anchor prepares run concurrently; the decision needs one more anchor proposal. On an eligible single-partition transaction, initialization, preparation, and decision share one proposal. Deferred settlement removes materialization from the client-visible path in either case (Table I).

Per-key actors make key-local mutation sequential and keep critical sections explicit. Consensus I/O is submitted off the mailbox, so unrelated reads or lock-release messages do not wait for a network round trip. Participant work is grouped by partition, validation uses batched probes instead of one remote request per key, and prepare deltas are serialized once before any retry loop. Bounded mailboxes, queue byte caps, transaction timeouts, participant-effect leases, and terminal reservations constrain retained state under overload, and they make overload visible as backpressure or retry rather than as unbounded allocation.

What the design costs

A persistent transaction creates an anchor record and one prepared intent per written key, performs validation probes, and later materializes and removes each intent. Deferred settlement moves work out of foreground latency, but it lengthens the interval during which readers consult transaction records and writers help predecessors. Heterogeneous batching trades up to the linger interval for density. Pessimistic scans can restrict concurrency over large ranges. Snapshot holds increase revision retention and backend space. The system exposes metrics for queueing, batch fill, settlement failure, recovery, and WAL phases, so these trade-offs can be measured instead of inferred from throughput alone.

XI. What an Answer Means

A distributed client must interpret each outcome conservatively:

  • Committed: the canonical persistent decision is commit, and every participant effect was prepared before that decision. Materialization may still be running.
  • Aborted: a canonical terminal abort exists, from a conflict, an explicit rollback, a failed validation, or presumed abort. New work needs a new transaction.
  • MustRetry: no safe terminal answer was established at this boundary. Retry with the same transaction handle and, for an operation, the same operation identifier.
  • AdmissionRefused: no transaction started; back off or lower the load.

A timeout or a lost connection is not proof of abort. Starting an unrelated replacement transaction can duplicate application effects if the original later proves committed. Durable handles, operation digests, terminal-result retention, and canonical anchor lookup make same-identity retry the natural safe behavior.

Direct non-transactional writes have a different retry contract. If the transport reports an indeterminate outcome and the operation lacks an application idempotency key, a blind replay can repeat a condition or a mutation. The stronger operation registry belongs to interactive transactions.

XII. Relationship to Prior Systems

The foundation is conventional in the best sense. Raft replicates partition state [3], HLCs give causality-compatible timestamps [5], and two-phase commit separates participant preparation from a terminal decision [7]. The interest lies in how those tools are composed around a key-actor data path.

Percolator builds distributed transactions over a key–value substrate with timestamped locks and a distinguished primary [8]. Kahuna's anchor record plays a related decision-authority role, but the record is an explicit replicated state machine, the participant effects are typed Raft entries, and the live coordinator supports both locking and validation policies. CockroachDB also uses transaction records, write intents, MVCC, and asynchronous intent resolution [9]. Kahuna shares the principle that a committed logical value can be read through an unresolved intent; its emphasis is the integration with per-key actors, heterogeneous proposal batching, explicit range-generation fences, and server-owned interactive sessions. FoundationDB uses optimistic conflict ranges and presents strict serializability [10]. Kahuna's optimistic point validation checks declared dependencies in a similar spirit, but it does not turn every optimistic scan into a conflict range, so its guarantee is intentionally more conditional. Spanner combines 2PC, Paxos, MVCC, and TrueTime for external consistency [6]; Kahuna uses HLC without a commit-wait protocol and makes no external-consistency claim. Calvin orders transactions deterministically in advance [11]; Kahuna instead supports interactive transactions whose read and participant sets emerge during execution, and it pays prepare and decision coordination to keep that flexibility.

No individual mechanism is claimed to be new. The notable features are combinations: atomic anchor initialization plus anchor preparation, with an eligibility-checked one-proposal fast path; exact-value prepared intents that double as the read overlay during deferred settlement; a three-layer lost-update defense that ends in participant-replica abort assistance; adaptive HLC decision deadlines that make presumed abort a replicated state transition; range-move refusal until decision overlays are safe to transfer; heterogeneous batching across unrelated entries that keeps per-item fencing and completion; and a server-owned idempotency registry joined atomically with finalization admission. Their value is the reduction of gaps between the protocol and the operational realities of actors, retries, reconfiguration, and asynchronous persistence.

XIII. Limits and Threats to Validity

First, this analysis is tied to one source snapshot and its documented tests. It is not a formal proof. The code contains deterministic state machines and focused fault tests, but an implementation can still violate a derived invariant through an unmodeled path.

Second, the strongest isolation statement depends on configuration. Optimistic point reads are validated, but optimistic scans validate returned keys rather than gaps, so phantoms remain possible. Pessimistic predicate locks are leased, in-memory, and leader-local. Fixed historical snapshots protect time-consistent reads and retention, not the serialization of later writes. Shared point-read locks are not yet implemented.

Third, crash atomicity covers the persistent participant set in durable mode. Ephemeral participants are unrecoverable by nature, and a mixed best-effort transaction can become partially visible after a crash.

Fourth, availability of two-phase commit is bounded by consensus and decision recovery. A partition that cannot reach quorum cannot decide safely. Presumed abort limits indefinite orphan blocking after a deadline; it does not create availability during quorum loss.

Fifth, the most recent per-key failover hardening needs more empirical validation. A partition and kill campaign found executions in which a promoted node combined an orphaned prepared intent with stale per-key committed-head state, which allowed acknowledged results to fork after failover. Kahuna 1.5.3 adds the replica-side stale-base veto, and the focused tests are green, but the acceptance gate still calls for an extended multi-node fault soak. Until that gate passes, the proper claim is “designed and locally validated to close the stale-leader gap”, not “demonstrated under the full campaign”.

Finally, this note reports no fresh benchmark. The one-phase path, batching, and deferred settlement remove or amortize identifiable work; actual throughput, tail latency, recovery time, and storage amplification require reproducible experiments across contention levels, participant counts, backends, and fault schedules.

XIV. Conclusion

Kahuna's persistent transaction system is organized around one compact safety idea: prepare every exact participant effect durably, choose one canonical outcome, and make every read, retry, recovery worker, and range move honor that outcome until ordinary storage catches up. The surrounding subsystems exist to preserve that idea at their boundaries. Actor ownership prevents local races; operation identities prevent duplicate effects; locks and validation protect declared dependencies; base fences close read-to-prepare races; Raft makes records and intents replayable; decision-aware reads permit deferred materialization; deadlines and tombstones resolve abandoned work; and range barriers keep reconfiguration from dropping unresolved state.

The design brings a durable, recoverable transaction core to a high-performance actor-based key–value layer without forcing every workload through one concurrency policy. That flexibility is also why its guarantees must be stated precisely. Persistent-only durable transactions, complete dependency tracking, and predicate locking where phantoms matter support strong executions. Permissive reads, optimistic scans, historical writes, or ephemeral participants deliberately weaken the result. The clearest description is not a single isolation label, but a protocol core plus an explicit guarantee envelope.
